# ReachInbox Assignment Reference Document

# Real-Time AI Email Onebox

## Phase 0: Project Setup and Architecture Overview

The core architecture consists of three main components: **IMAP Sync Service**, **Persistence Layer (Elasticsearch/Vector DB)**, and **API/Web Integration Layer (Node.js/TypeScript)**.

### 0.1 Initializing the Project

1. **Create Project Directory:**
    
    ```
    mkdir reachinbox-onebox
    cd reachinbox-onebox
    npm init -y
    ```
    
2. **Initialize TypeScript:**
    
    ```
    npm install typescript @types/node ts-node --save-dev
    npx tsc --init # Configure tsconfig.json
    ```
    
3. **Install Core Dependencies:**
    - **IMAP Client:** `npm install node-imap` or `mailjs/imap-client`
    - **Elasticsearch Client:** `@elastic/elasticsearch`
    - **Express/Koa:** `express` for the REST API
    - **Environment Variables:** `dotenv`
    - **LLM API:** Install the necessary SDK or prepare to use native `fetch` for the Gemini API.

### 0.2 Docker Setup for Persistence

We need two containers: **Elasticsearch** (for searching) and a **Vector Database** (for RAG).

1. **Create `docker-compose.yml` (Complete Configuration):** Set up Elasticsearch and Qdrant (as a vector database example).
    
    ```
    version: '3.8'
    services:
      # 1. Elasticsearch for Full-Text Search
      elasticsearch:
        image: docker.elastic.co/elasticsearch/elasticsearch:7.17.1
        container_name: es-onebox
        environment:
          - discovery.type=single-node
          - xpack.security.enabled=false
          - "ES_JAVA_OPTS=-Xms512m -Xmx512m"
        ulimits:
          memlock:
            soft: -1
            hard: -1
        volumes:
          - esdata:/usr/share/elasticsearch/data
        ports:
          - 9200:9200
        healthcheck:
          test: ["CMD-SHELL", "curl -f http://localhost:9200 || exit 1"]
          interval: 30s
          timeout: 10s
          retries: 5
    
      # 2. Qdrant (Vector Database) for RAG
      qdrant:
        image: qdrant/qdrant
        container_name: qdrant-onebox
        ports:
          - 6333:6333 # REST API
          - 6334:6334 # gRPC
        volumes:
          - qdrant_storage:/qdrant/storage
    
    volumes:
      esdata:
        driver: local
      qdrant_storage:
        driver: local
    
    ```
    
2. **Start Services:** Run `docker-compose up -d`.

## Phase 1: Real-Time Email Synchronization (IMAP IDLE)

This is the most critical backend requirement. **Polling is forbidden.**

### 1.1 IMAP IDLE Implementation

The IMAP `IDLE` command is used to listen for changes on the server in real-time without constant polling.

1. **Persistent Connection:** Use an IMAP library to establish and maintain a connection for each account.
2. **Authentication:** Securely store and retrieve credentials for at least two test accounts (e.g., using secure environment variables).
3. **Initial Sync (History):**
    - Upon first connection, fetch all necessary folders (INBOX, Sent, etc.).
    - Use IMAP search criteria (e.g., `SINCE` 30 days ago) to fetch the initial batch of emails.
    - For each email, fetch the `ENVELOPE` (metadata) and `BODYSTRUCTURE` (to identify attachments/parts). **Do not fetch the full body content yet.**
4. **Real-Time Listener (IDLE):**
    - Once the initial sync is complete, transition the connection to `IDLE` mode.
    - The connection will emit events (e.g., `mail` or `expunge`) when a new email arrives or one is deleted.
    - When a new email is detected, fetch only that email's data and pass it to Phase 2.
    - **Connection Maintenance:** Implement a watchdog to check the IDLE connection periodically (e.g., every 29 minutes, as IDLE timeouts are common) and re-send the IDLE command to keep the session alive.

### 1.2 Data Structure Mapping

Define a TypeScript interface for the email data to be stored:

```
// Conceptual Interface
interface EmailDocument {
    id: string; // Unique message ID
    accountId: string;
    folder: string; // INBOX, Sent, etc.
    subject: string;
    body: string; // Plain text content
    from: string;
    to: string[];
    date: Date;
    aiCategory: 'Interested' | 'Meeting Booked' | 'Not Interested' | 'Spam' | 'Out of Office' | 'Uncategorized';
    // Elasticsearch metadata
    indexedAt: Date;
}

```

## Phase 2: Searchable Storage using Elasticsearch

Emails must be indexed immediately after they are received from the IMAP sync.

### 2.1 Indexing Emails

1. **Initialize Elasticsearch Client:** Connect your Node.js application to the Dockerized Elasticsearch instance (`http://localhost:9200`).
2. **Define Mapping:** Create a specific index (e.g., `emails`) with a proper mapping. You must ensure fields like `subject` and `body` are indexed for full-text search, while fields like `accountId` and `folder` are indexed as keywords for fast filtering.
    
    ```
    // Conceptual Elasticsearch Index Mapping setup
    await client.indices.create({
        index: 'emails',
        mappings: {
            properties: {
                subject: { type: 'text' },
                body: { type: 'text' },
                accountId: { type: 'keyword' },
                folder: { type: 'keyword' },
                date: { type: 'date' },
                aiCategory: { type: 'keyword' }
            }
        }
    });
    ```
    
3. **Indexing Logic:** When a new email arrives (Phase 1), strip the HTML/get the plaintext body, map it to the `EmailDocument` interface, and send it to Elasticsearch via the `index` API.

### 2.2 Search and Filtering Implementation

Implement a basic API endpoint (`/api/emails/search`) that accepts search terms, filters, and pagination parameters.

1. **Query Structure (Basic Search):** Use the `query_string` or `multi_match` query to search across the `subject` and `body` fields.
2. **Filtering:** Use the `must` clause inside a `bool` query or the `filter` clause for exact matches on `folder` and `accountId`. This ensures filtering is fast and does not affect the search score.
    
    ```
    // Conceptual Search Query Body for Elasticsearch
    const esQuery = {
      query: {
        bool: {
          must: [
            { multi_match: { query: 'search term', fields: ['subject', 'body'] } }
          ],
          filter: [
            { term: { accountId: 'user@example.com' } }
          ]
        }
      }
    };
    ```
    

## Phase 3: AI-Based Email Categorization (Gemini API)

This step uses an LLM (via the Gemini API) to classify the emails. This avoids building and training a custom model.

### 3.1 LLM Categorization Service

1. **System Prompt:** Define a precise `systemInstruction` to tell the model its role and the required output format.
2. **JSON Schema:** Use the `generationConfig` with `responseMimeType: "application/json"` and a specific `responseSchema` to guarantee the model returns only one of the five required labels.
    
    ```
    // Conceptual System Instruction and Schema
    const systemInstruction = "You are an expert email classifier. Your task is to analyze the provided email text and categorize it into one of the following labels: Interested, Meeting Booked, Not Interested, Spam, or Out of Office.";
    
    const responseSchema = {
      type: "OBJECT",
      properties: {
        category: {
          type: "STRING",
          enum: ["Interested", "Meeting Booked", "Not Interested", "Spam", "Out of Office"]
        }
      }
    };
    ```
    
3. **Integration:** Every new email indexed in Phase 2 must be passed to this service. The resulting `aiCategory` is then updated in the Elasticsearch document (Phase 2).
4. **Error Handling:** Implement exponential backoff for API calls to gracefully handle rate limits or temporary errors.

## Phase 4: Slack & Webhook Integration

Triggering external actions based on the `Interested` category.

### 4.1 Integration Logic

1. **Trigger Point:** Integrate this logic immediately after the AI Categorization service (Phase 3) returns a result of **'Interested'**.
2. **Slack Notification:**
    - Obtain a Slack Incoming Webhook URL (for development, you can create one for a test workspace).
    - Send a `POST` request to the Slack URL with a JSON payload, including the email's subject, sender, and a link to the email in your app (if applicable).
3. **Generic Webhook Trigger:**
    - Use `https://webhook.site` to get a temporary URL. This will act as the external automation endpoint.
    - Send a second `POST` request to this webhook URL. This payload should contain all relevant email data for external consumption.
    
    ```
    // Conceptual Webhook Sending Function
    async function triggerWebhook(emailData) {
      const webhookUrl = process.env.WEBHOOK_SITE_URL;
      const slackUrl = process.env.SLACK_WEBHOOK_URL;
    
      // 1. Slack Notification
      await fetch(slackUrl, { /* ... payload for Slack ... */ });
    
      // 2. Generic Webhook for Automation
      await fetch(webhookUrl, {
        method: 'POST',
        headers: { 'Content-Type': 'application/json' },
        body: JSON.stringify({ event: 'InterestedLead', email: emailData })
      });
    }
    ```

## Phase 6: AI-Powered Suggested Replies (RAG)

This requires implementing a Retrieval-Augmented Generation (RAG) pipeline to fetch context from a Vector Database before generating the LLM response.

### 6.1 Vector Database and Embeddings Setup

1. **Vector DB (Qdrant/Weaviate):** Ensure your Dockerized vector DB is running (Phase 0).
2. **Product Data Storage:** Store your "product and outreach agenda" (e.g., meeting links, product features, common answers) as chunks of text in the vector database.
3. **Embeddings Generation:**
    - You need an embedding model to convert the text chunks into dense vectors. The Gemini API can be used for this (`models/embedding-001` or similar).
    - For each piece of product data, call the embedding API, and then store the resulting vector and the original text in the vector database.

### 6.2 The RAG Pipeline - Step-by-Step Flow

The RAG process is an advanced feature and requires coordination between the email data, the vector database, and the LLM.

1. **API Endpoint:** Create a new endpoint: `POST /api/emails/:id/suggest-reply`.
2. **Input:** User selects an email and hits "Suggest Reply." The backend receives the full text of the original incoming email.
3. **Retrieval Query:** The original incoming email text is sent to the **Embedding Model (Gemini API)** to be converted into a query vector.
4. **Vector Search:** The query vector is sent to the **Vector Database (Qdrant)**.
5. **Context Retrieval (R):** The Vector Database returns the top $K$ (e.g., $K=3$) most relevant chunks of **Product Data/Outreach Agenda** (e.g., the meeting link, the specific product pricing).
6. **Prompt Assembly:** A final, comprehensive prompt is constructed for the LLM. This prompt *must* contain:
    - **System Instruction:** Act as a helpful assistant that writes professional, relevant email replies.
    - **Retrieved Context:** The text chunks retrieved from the Vector DB (Step 5).
    - **Original Email:** The full text of the email received from the user (Step 2).
    - **Final Instruction:** "Based ONLY on the context provided and the original email, draft a professional and helpful reply. Be concise."
7. **Generation (G):** The combined prompt is sent to the **Generative LLM (Gemini API)**.
8. **Output:** The LLM's response (the suggested reply) is returned to the Frontend UI.

## External References and Learning Resources

To assist in tackling the specific technical challenges, here are key resources and documentation links:

1. **IMAP IDLE and Real-Time Sync:**
    - **`node-imap` Documentation:** Focus on the `imap.on('mail', ...)` event and the `imap.idle()` method documentation for setting up the non-polling listener.
    - **IMAP Protocol Basics:** Understand the `IDLE` command itself and the typical timeout mechanisms (e.g., 30 minutes) which necessitate the connection maintenance/watchdog.
2. **Elasticsearch (Indexing and Searching):**
    - **Official Elastic.co Documentation (for Node.js):** Refer to the official `@elastic/elasticsearch` client guide for connecting, creating indices (`client.indices.create`), and executing searches (`client.search`).
    - **Query DSL Guide:** Learn about `bool` queries, `multi_match` for general search, and `term`/`keyword` for precise filtering.
3. **Vector Databases and RAG:**
    - **Qdrant/Weaviate Documentation:** Look at the client libraries (e.g., Qdrant's Node.js client) for creating collections and performing **similarity search** (the "Retrieval" step).
    - **RAG Conceptual Overview:** Search for Retrieval-Augmented Generation tutorials to reinforce the concept of using vectors to inject context into the LLM prompt.
4. **Gemini API (Classification and Embeddings):**
    - **Gemini API Documentation (General):** Understand how to structure `generateContent` requests.
    - **JSON Mode:** Crucial for Phase 3. Look up how to specify `responseMimeType: "application/json"` and `responseSchema` to guarantee structured output for email categorization.
    - **Embedding Model:** Review the documentation for the embedding model (`models/embedding-001` or similar) to correctly convert text into vectors for the Vector DB (Phase 6.1).
5. **Typescript and Node.js Best Practices:**
    - **Dependency Injection/Modular Architecture:** Resources on structuring large Node.js applications with Typescript to maintain clean, scalable code as required by the assignment evaluation criteria.
